# 四、raw.md 必须保留 PAGE 标记

当前逐页 Markdown 中：

```html
<!-- PAGE: 0001 -->
```

Phase 7：

**继续保留。**

不要删除。

例如：

```md
<!-- PAGE: 0001 -->

# Chapter 1

...

<!-- PAGE: 0002 -->

...
```

原因：

后续出现：

```text

表格错误
图片错误
Cleaner误修改
```

仍能快速追踪 PDF 原页。

PAGE marker 直到后续 Cleaner / Final 阶段才删除。

# 二十五、PAGE marker 校验

每一物理页：

应有且仅有一个：

```html

```


# 二十六、PAGE marker 自动标准化是允许的



# 三十三、Continuity Candidate 来源

```text

```

另外可增加轻量 heuristic：

```text

```

但是 heuristic 只能：

```text
候选
```

不能自动修改。

# 四十、JOIN_WITH_SPACE

例如：

Page 10：

```text
This method can be
```

Page 11：

```text
used for...
```

patch：

```text
JOIN_WITH_SPACE
```

```text
This method can be <!-- PAGE boundary metadata -->

```

但 PAGE marker仍需存在。

# 四十一、PAGE marker与Join共存方式

推荐：

```md
This method can be
<!-- PAGE: 0011 -->
used for...
```

如果 downstream Markdown 中注释不会影响文本阅读：

这是最安全方式。

不要为了视觉连续：

删除 PAGE marker。

---

# 四十二、JOIN_WITHOUT_SPACE

适合：

```text

```

Page 1：

```text

```

```text
mation
```

但是：

自动去掉连字符非常危险。

所以：

```text

```

必须人工明确选择。

这阶段完成后，我最关心四个验收数字：

**`PAGE marker = 8`、`未解决 FIGURE marker = 0`、`无效图片路径 = 0`、第二次 Assemble = CACHED。**

如果这四项都成立，再加上 `markdown_pages / resolved_pages / figures` 的 SHA256 全部没变化，那么整个项目的数据链条就非常清楚了：

```text
Immutable-ish upstream assets
        ↓
resolved page assets
        ↓
deterministic assembly
        ↓
raw.md
```

下一阶段的 Cleaner 才可以放心作为一个**新的派生层**运行，而不是偷偷破坏已经验证过的文本和图片资产。

另外，我仍建议 Phase 7 **不要自动修跨页句子**。先把 candidate 和人工 patch overlay 做好。如果未来一本 300 页数学书只有十几个跨页候选，人工确认其实很快；如果发现有上百个，再值得单独设计 AI Continuity Repair。
