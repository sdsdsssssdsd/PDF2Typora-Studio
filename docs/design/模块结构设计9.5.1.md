可以，而且我认为这反而是现在**最值得走的路线之一**。

你描述的思路本质上是：

```text
页面图片
↓
OCR / 文档解析
↓
文字 + 坐标 + 表格 + 公式 + Caption
↓
DeepSeek 文本 API
↓
结构重建成 Markdown
```

这和“DeepSeek API 没有 Vision”并不冲突。DeepSeek 官方公开 API 目前仍以文本请求为主，官方文档没有给出通用图片输入接口，因此让**本地 OCR/文档解析器负责“看”**，DeepSeek API 负责**理解结构、重建 Markdown、修格式**，是很合理的分工。([DeepSeek API 文档][1])

而且我会进一步改成：**不要“纯 OCR → DeepSeek”，而是“PDF 原生文本 + OCR + Layout → DeepSeek”三路融合。**

## 我建议的新页面转录架构

```text
                         PDF Page
                            │
          ┌─────────────────┼──────────────────┐
          ▼                 ▼                  ▼
    PyMuPDF Text        Page Image        PDF Objects
      Layer                │                  │
          │                ▼                  ├─ raster images
          │          PaddleOCR                ├─ vectors
          │          / PP-StructureV3         └─ captions
          │                │
          ▼                ▼
  text/font/bold/       OCR text
  color/bbox            bbox/layout
          │                │
          └────────┬───────┘
                   ▼
            Page Evidence JSON
                   │
                   ▼
             DeepSeek API
             （纯文本输入）
                   │
                   ▼
           Structured Markdown
                   │
                   ▼
          Coverage / Fidelity Validator
```

这会比现在“Gemma 看整页然后自己抄”可靠很多。

PaddleOCR 目前官方的 PP-OCRv5 就是专门的文字识别管线；而 **PP-StructureV3** 已经不仅是 OCR，它还支持版面解析、表格识别、公式识别、图表理解、阅读顺序恢复以及转换为 Markdown，很适合拿来做我们这里的“页面预处理器”。([PaddlePaddle][2])

## 关键点：不是所有 PDF 都应该先 OCR

我们要分两种页面。

### 1. 有正常文字层的 PDF

像大部分论文、电子教材：

```text
PDF Text Layer
↓
作为正文第一真值
```

因为 PyMuPDF 能直接得到 span 的：

```text
text
font
size
flags
color
bbox
```

所以**漏字、粗体、颜色**应该优先从这里解决。官方文档明确说明 span 共享相同的字体属性，并包含字体、flags、颜色等信息。([PyMuPDF 文档][3])

OCR 这时的任务是：

```text
第二路校验
```

例如：

```text
PDF text:
The experiment used 256 samples.

OCR:
The experiment used 256 samples.

→ 高置信度
```

如果：

```text
PDF text:
The experiment used samples.

OCR:
The experiment used 256 samples.

→ TEXT_LAYER/OCR DISAGREEMENT
→ Review或让DeepSeek结合上下文处理
```

这就能真正解决你说的**文本内容识别不全**。

---

### 2. 扫描版 / 文字层坏掉的 PDF

如果：

```text
text layer empty
```

或者很多乱码、`U+FFFD`、覆盖率特别低，就直接：

```text
OCR / PP-StructureV3
↓
作为主要文字来源
```

PyMuPDF 官方也指出某些 PDF 内部编码可能被打乱，此时直接抽文本可能不可靠。([PyMuPDF 文档][4])

所以最终应该有：

```text
PageTextSourceMode

PDF_NATIVE
PDF_NATIVE_PLUS_OCR
OCR_PRIMARY
OCR_ONLY
```

自动选，不需要用户每页判断。

# DeepSeek 在这里负责什么？

**不要让 DeepSeek“重新猜文字”。**

给它这种输入：

```json
{
  "page": 4,

  "blocks": [
    {
      "id": "b001",
      "type": "heading",
      "text": "3. Experimental Results",
      "bbox": [91, 83, 702, 126],
      "bold": true,
      "color": "#000000"
    },
    {
      "id": "b002",
      "type": "paragraph",
      "text": "The experimental results ...",
      "bbox": [...]
    },
    {
      "id": "t001",
      "type": "table",
      "cells": [...]
    },
    {
      "id": "f001",
      "type": "figure_group",
      "label": "Fig. 2",
      "subfigures": ["a", "b", "c", "d"]
    }
  ]
}
```

然后告诉 DeepSeek：

> 只能使用这里提供的内容，不能补写任何文字。
> 按阅读顺序重建 Typora Markdown。
> 保留全部 block 内容。
> FigureGroup 只能输出指定 marker。
> 数字、公式、表格 cell 不得修改。

DeepSeek擅长的部分变成：

```text
理解层次结构
决定标题层级
把OCR块拼成段落
重建表格Markdown
整理公式格式
处理断行
```

而不是：

```text
从像素里辨认一个“5”到底是不是“6”
```

这样靠谱得多。

# 你的 5 个问题会分别怎么处理

### （1）Fig-1 漏掉

不再依赖 OCR/DeepSeek 是否说“这里有图”。

FigureGroup 独立由：

```text
PDF image/vector candidates
+
PP-Structure layout
+
OCR caption:
"Fig. 1 ..."
```

发现。

然后做：

```text
PDF发现Fig.1
但DeepSeek输出没有Fig.1 marker

→ BLOCKING
FIGURE_GROUP_MISSING_IN_MARKDOWN
```

**绝不能再静默漏掉。**

---

### （2）Fig-2 放成 Fig-3

继续坚持你刚刚定的规则：

```text
Fig. 2
├─ a
├─ b
├─ c
└─ d

= 一整张图片
```

身份以：

```text
Fig编号
+
Caption
+
bbox
```

为准。

不是 `figure_index`。

所以：

```text
Fig.2 ≠ 第二个检测框
Fig.3 ≠ 第三个检测框
```

这两个概念以后彻底拆开。

---

### （3）莫名 `\n`

OCR出来的文本本身就应该是：

```text
真实换行
```

进入 DeepSeek 前建立规范化层。

DeepSeek返回 JSON 后也必须先：

```text
JSON decode
↓
EscapeSanitizer
↓
Markdown
```

同时保护：

```latex
\nu
\neq
\nabla
```

所以这个是程序问题，不应该靠模型训练。

---

### （4）颜色和粗体

有文字层：

**直接相信 PDF span 样式。**

例如：

```text
text = "Important"
bold = true
color = #d70000
```

输出：

```html
<span style="color:#d70000">**Important**</span>
```

Typora 支持内联 HTML，所以这个方向可行。

OCR 只负责文字，不负责覆盖 PDF 已有的样式信息。

扫描 PDF 才需要额外做：

```text
OCR bbox
+
区域颜色采样
+
字体粗细估计
```

这部分精度会比 born-digital PDF 低，需要标 confidence。

---

### （5）漏文本

以后增加一个硬指标：

```text
Text Coverage
```

例如：

```text
PDF native chars: 4281
OCR chars:        4310
Markdown chars:   4268
```

以及 block coverage：

```text
Source blocks:    73
Covered blocks:   72

Coverage:
98.63%
```

如果某一个 OCR/PDF block 在最终 Markdown 根本找不到：

```text
UNCOVERED_SOURCE_BLOCK
```

不能自动通过。

这正是现有 Vision-only Pipeline 缺的东西。

现在先做：

## **Phase 9.5.1 — OCR + DeepSeek Reconstruction**

核心：

```text
PDFTextStyleExtractor
        +

        ↓
PageEvidenceManifest
        ↓
DeepSeek Text API
        ↓
Markdown
        ↓
Coverage Validator
        ↓
```

而且必须加入一个模式切换：

```text
页面转录引擎：

○ Vision Only（旧版，保留用于比较）

● Hybrid OCR + API（推荐）

○ PDF Native + OCR + Local LLM

○ Document Parser Only
```

这样我们可以拿同一页直接 A/B：

```text
旧 Gemma Vision
vs
PDF + OCR + DeepSeek
```

然后看：

```text
漏字数量
Figure漏识别数量
Figure错配
表格完整率
粗体还原率
颜色还原率
人工Review数量
```

如果第二条明显胜出，就正式把它作为默认 Pipeline。

## 训练应该再往后一步

这个新 Pipeline 同时继续收集：

```text
原始页面
PDF spans
OCR结果
Layout结果
DeepSeek输出
人工修正最终Markdown
FigureGroup
```

等你处理了几十或几百页真正教材以后，再进入：

```text
Phase 9.6
Domain Fine-tuning / LoRA
```

PaddleOCR 官方本身也提供已有预训练模型以及 fine-tuning 路线，因此完全没必要从零训练 OCR。([PaddleOCR][6])

**我的建议是：下一阶段先不要训练。先把 `PaddleOCR/PP-Structure + PDF 原生文本 + DeepSeek API` 接起来。** 这条路线能直接针对你现在遇到的漏字、粗体颜色、`\n`、Figure 漏掉和 Figure 错配五类实际问题，而训练一个通用 Vision 模型并不能同时可靠解决它们。
