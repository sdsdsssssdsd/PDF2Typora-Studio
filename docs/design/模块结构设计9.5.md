而且这 5 个问题其实指向同一个根因：我们之前太依赖“整页图片 → 一个通用 Vision 模型 → Markdown”。下一步应该改成 **PDF 原生信息 + 文档专用模型 + Vision/API 三路融合**，而不是单纯训练 Gemma。

## 先说“训练模型”：有现成的，而且应该先用现成的

我不建议现在就自己训练一个模型。

目前已经有更针对“PDF/文档解析”的预训练方案。例如 **PaddleOCR-VL-1.6** 是 2026 年发布的专用文档解析方案，官方重点就是文本、公式、表格、图表、复杂版面解析；前一代 1.5 是 0.9B 级别模型，并支持文档元素定位、跨页表格和多级标题。官方还已经提供 API SDK。([GitHub][1])

**MinerU** 更像完整 PDF→结构化文档引擎，本身就做阅读顺序、图片、图注、表格、公式 LaTeX、多栏布局，并输出 Markdown/JSON；它甚至提供布局/span 可视化，非常适合拿来作为我们现有 Pipeline 的第二路解析结果。([GitHub][2])

**Qwen3-VL** 也值得继续测，但用途应该改成“视觉补充/校验/定位”，而不是唯一真值。官方目前强调其 OCR、长文档结构解析和 2D grounding；也有 2B/4B/8B 等版本。([GitHub][3])

训练不是取消，而是**延后**。我们应该先让软件自动积累你人工修正过的数据：

```text
页面PNG
+ PDF原生文字/span/layout
+ 正确Markdown
+ 正确Figure bbox
+ Figure与caption对应关系
+ bold/color样式
```

累计几十到几百页以后，再做 LoRA/SFT 才有意义。Qwen 官方已经提供过 VL fine-tuning 代码，PaddleOCR-VL 也有官方 SFT 路线。([GitHub][3])

# 你列的 5 个问题，我建议这样根治

1. **Fig-1 完全漏掉**

这是当前架构的一个真正缺陷：

```text
以前：
AI说“这里有图”
↓
Figure Pipeline才去找图
```

应该反过来：

```text
PDF每页
↓
先独立发现所有视觉候选
├─ embedded raster
├─ vector cluster
├─ chart/figure layout region
└─ caption
↓
形成 PageLayoutManifest
↓
再与AI结果对账
```

也就是说，即使 Gemma 完全没说 Fig-1 存在，只要 PDF 结构或文档 Layout 模型发现了一个明显 Figure，系统就必须报告：

```text
UNREFERENCED_FIGURE_CANDIDATE
```

而不是让它凭空消失。

这会直接修复你的第（1）类问题。

---

2. **Fig-2 却插成 Fig-3**

以后**彻底取消“按 index 直接配图”**。

现在这种：

```text
AI Figure index=2
→ pXXXX_fig02
```

风险太大。

改成稳定身份：

```text
candidate_id =
page
+ bbox
+ PDF xref/digest
```

然后通过：

```text
空间位置
+ caption位置
+ caption文字
+ bbox重叠
```

匹配。

例如 PDF 原生文本检测到了：

```text
Figure 2. ...
```

它下面最近的视觉区域才是 Figure 2。

Figure 3 同理。

最终：

```text
Figure编号 ≠ 数组下标
```

数组下标只用于显示，不能作为图像身份。

---

3. **正文出现莫名的 `\n`**

这个不需要模型训练，属于程序 bug / 输出协议问题。

应该增加一个：

```text
MarkdownEscapeSanitizer
```

区分：

```text
真实换行符：
\n 作为字符编码后的 newline

错误文字：
反斜杠 + n
```

尤其模型 JSON：

```json
{
  "markdown": "abc\nxyz"
}
```

经过 JSON decoder 后应该成为真正换行：

```text
abc
xyz
```

不能最终写成：

```text
abc\nxyz
```

另外必须避免误伤 LaTeX，比如：

```text
\nu
\neq
\nabla
```

所以不能简单：

```python
text.replace("\\n", "\n")
```

要在 Markdown/LaTeX scanner 外层做安全转换。

这个应该直接加入回归测试。

---

4. **颜色、粗体没有还原**

这里反而**不应该靠 Vision 模型猜**。

PyMuPDF 已经能从 PDF text span 中拿到：

```text
text
font
font size
flags
color
bbox
```

官方文档明确说明 span 是由相同字体属性的字符组成，而且 `flags` 可以识别 bold/italic，`color` 能得到文本颜色。([PyMuPDF 文档][4])

也就是说，如果 PDF 是 born-digital，我们应该直接得到：

```text
"This is important"
font = ...
bold = true
color = #E60012
bbox = ...
```

然后输出：

```md
**This is important**
```

如果原 PDF 是红色：

```html
<span style="color:#e60012">This is important</span>
```

Typora 官方明确支持 inline HTML `<span style="color:...">`，所以颜色是可以保留下来的。([Typora 支持][5])

如果同时粗体+红色，可以生成类似：

```html
<span style="color:#e60012">**This is important**</span>
```

这里要改变我们以前的规则：

> 不再是“绝对禁止 `**`”。

而是：

> **禁止模型擅自加粗，但如果 PDF 源 span 明确是 bold，就必须还原为 `**...**`。**

这完全符合你现在想要的“一点不变”。

---

5. **文本内容识别不全**

这是最重要的。

对于**有 text layer 的 PDF**，Vision 不应该再负责从零抄全文。

新的优先级应该是：

```text
PDF Text Layer
    ↓
得到原始文字 + bbox + font + color + bold
    ↓
Document Layout Engine
    ↓
确定阅读顺序 / 标题 / 表格 / 图位置
    ↓
Vision Model
    ↓
只负责：
公式
复杂表格
扫描区域
图片理解
text layer异常区域
视觉校验
```

PyMuPDF 官方也提醒，PDF 文本可以直接抽取，但自然阅读顺序有时不可靠，因此我们应该使用 block/span 坐标再结合 Layout Engine，而不是单纯 `get_text("text")`。([PyMuPDF 文档][4])

这样即使 Vision 漏一句：

```text
PDF text layer里面有
↓
Coverage Validator发现Vision漏了
↓
不能自动通过
```

我们以后可以直接计算：

```text
PDF source text coverage: 99.2%
Markdown coverage: 94.3%

→ FAIL / REVIEW
```

这比现在“模型自己说 needs_review=false”可靠太多。

### Figure 的身份层级应该改成

```text

├── bbox = 包含 a+b+c+d 的整体区域
```
