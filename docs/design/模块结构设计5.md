有一个重要调整：Ollama 官方 Structured Outputs 文档建议把 JSON Schema 同时放入 `format` 和 Prompt 来帮助模型理解；但你在 8GB 显存、4K 上下文的真实测试已经证明，**完整 Schema 进入 Prompt 会造成 context overflow，甚至诱发 Prompt 内容污染**。因此这里有意采用“`format=完整 Schema` + Prompt 只保留极短字段语义说明”的策略。这是根据你机器上的实际结果做出的工程取舍。Ollama 的 `/api/chat` 本身支持 JSON Schema `format`，所以结构约束仍然存在。([Ollama][1])

另外，Ollama 当前在低于 24 GiB VRAM 时默认 4K context，而扩大 context 会增加内存需求；因此你的 8GB 4060 上应该做 **Auto → 必要时 8192 → OOM/失败则换模型**，而不是固定把所有模型拉到大 context。([Ollama][2]) 批处理时则应该让同一个主模型保持加载，避免你 Gemma 首次约 107 秒的 load 重复发生；Ollama API 的 `keep_alive` 正是为这个用途提供的，`0` 又可以在任务结束时立即卸载。([Ollama][3])

我这次最想看的是两个数字：**首次 8 页 Batch 的 `AUTO_ACCEPTED / NEEDS_REVIEW / FAILED` 比例**，以及**第二次完全相同任务真实调用模型的次数**。如果第二次能做到 `0 次真实 AI 调用 + 8 页缓存命中`，说明你的整个 AI 层断点和缓存机制已经真正站住了。

还有一个变化我认为非常值得保留：**现在先不往每页请求里塞“上一页尾部”**。你已经亲眼碰到了 context 压力；而且一旦 Page 2 的 request hash 依赖 Page 1 文本，修改第一页可能导致后面一串页面缓存级联失效。先把每页独立转录稳定下来，只通过 `continues_from_previous / continues_to_next` 建立跨页候选，之后再用“相邻两页专门的 continuity pass”解决，会干净很多。

批处理期间让同一主模型维持加载也很重要。Ollama 默认会在一段时间后卸载模型，并允许请求级 `keep_alive` 控制生命周期；`/api/ps` 同时能返回正在运行模型的 `size_vram` 与 `context_length`，所以 VRAM 指标应该在模型仍加载时采样，而不是 `keep_alive=0` 之后才读取。([Ollama][3])

等这一阶段回来，你最初的人工流程里最耗人的一段——**“每十页上传一次 → 等回复 → 复制 Markdown → 再处理下一批”**——就基本真正消失了。下一步才值得去攻现在另一个人工大头：**FIGURE marker → 自动定位 → 自动裁图 → figures/ → 相对路径替换**。
