对，**单纯 OCR 不应该成为主架构**。我查了一圈 GitHub 里现在比较成熟的 PDF→Markdown / 文档理解项目，比较适合你的不是“找一个 OCR 替代 Gemma”，而是**借它们已经验证过的混合架构**。

我最推荐你重点借鉴这 5 个项目：

| 项目                | 最值得借的东西                                             | 对你现在问题的价值                        |
| ----------------- | --------------------------------------------------- | -------------------------------- |
| **Marker**        | “文字层优先 → 必要时 OCR/VLM → Layout → Block 格式化 → 可选 LLM” | **最适合借整体 Pipeline 思想**           |
| **MinerU**        | 科研 PDF、阅读顺序、公式、表格、Figure/Caption、Layout JSON        | **最适合解决漏图、图注、复杂版面**              |
| **Docling**       | 统一 Document DOM、中间结构、lossless JSON                  | **最适合重构你的 PageEvidenceManifest** |
| **Chandra OCR 2** | 4B 文档专用视觉模型、layout blocks、表格/数学/图片                  | **值得直接替换 Gemma 做 A/B 实测**        |
| **olmOCR**        | 文档 VLM、复杂阅读顺序、公式/表格，以及完整训练代码/Benchmark              | **最适合未来训练和质量评测**                 |

## 1. 最值得你借的其实是 Marker 的思路

Marker 现在并不是“整页 OCR”。它的路线是：

```text
Extract text
↓
OCR/VLM only when necessary
↓
Layout + Reading Order
↓
Block cleaning / formatting
↓
Optional LLM improvement
↓
Markdown
```

官方现在甚至提供 `--disable_ocr`，对于有可靠文字层的 PDF 可以走纯文字层；同时它支持表格、公式、图片提取、Markdown/JSON，并允许 LLM 做增强。([GitHub][1])

这几乎就是我们现在应该把你的项目改成的逻辑。

### 也就是说不要：

```text
PDF
↓
OCR
↓
DeepSeek
```

而是：

```text
PDF
↓
页面分类
├─ Born-digital PDF
│   ├─ PDF text/style
│   ├─ Layout
│   └─ OCR/VLM only for suspicious blocks
│
└─ Scan PDF
    ├─ Layout
    ├─ OCR/VLM
    └─ structure recovery
↓
统一 Block DOM
↓
DeepSeek
↓
Markdown Reconstruction
```

**Marker 最值得借的是“模型按需介入”，而不是 OCR 全覆盖。**

# 2. MinerU 非常适合解决你现在的 Figure 问题

MinerU 本身就是科研文献场景出身。它官方明确支持：

* 单栏/多栏/复杂排版阅读顺序
* 图片及图片描述
* 表格及标题
* 公式 → LaTeX
* 扫描 PDF / 乱码 PDF 自动识别后启用 OCR
* Markdown / 阅读顺序 JSON / 中间结构
* layout/span 可视化 ([GitHub][2])

更重要的是，它现在的 Layout 分类本身就区分：

```text
chart
display_formula
figure_title
image
inline_formula
table
text
paragraph_title
header
footer
...
```

也就是说 `figure_title` 本身就是一级对象。([GitHub][3])

这正是你缺的。

你现在发生：

```text
Fig.1 直接消失
Fig.2 配到 Fig.3
```

根本原因就是现 Pipeline：

```text
模型先决定有没有图
↓
然后才去 PDF 找图
```

MinerU 思想应该倒过来：

```text
Layout Engine
↓
检测 Figure / Chart / Caption
↓
形成独立 FigureGroup
↓
再跟正文模型结果核对
```

以后：

```text
PDF/Layout发现 Fig.1
但Markdown没有 Fig.1
```

必须：

```text
BLOCKING:
FIGURE_GROUP_NOT_REFERENCED
```

绝对不允许自动通过。

# 3. Docling 最值得借的不是 OCR，而是“中间文档模型”

Docling 目前支持：

* page layout
* reading order
* table structure
* formulas
* image classification
* OCR
* VLM
* Markdown
* **lossless JSON**
* 一个统一的 `DoclingDocument` 表示 ([GitHub][4])

这个理念对你特别重要。

你现在已经有不少：

```text
PageTranscriptionResult
FigureGroup
PageLayoutManifest
PDF spans
AI response
```

但这些信息还是比较分散。

建议我们直接借 Docling 的思路，创建自己的：

# `DocumentPageModel`

例如：

```python
DocumentPage
├── page_number
├── width
├── height
│
├── blocks[]
│   ├── TextBlock
│   ├── HeadingBlock
│   ├── FormulaBlock
│   ├── TableBlock
│   ├── FigureGroup
│   ├── CaptionBlock
│   └── ListBlock
│
└── provenance
```

每一个 Block：

```python
block_id
type
bbox
reading_order
text
style
source
confidence
```

其中：

```text
source:
PDF_NATIVE
LAYOUT_ENGINE
OCR
VLM
MANUAL
```

最终 Markdown 不再直接由任何一个模型生成。

而是：

```text
DocumentPage
↓
MarkdownRenderer
```

这会是一个非常大的质量提升。

# 4. Chandra OCR 2 我认为非常值得拿来替换 Gemma 做实测

这个项目让我比较感兴趣。

目前 GitHub 的 Chandra OCR 2 是一个 **4B 专用文档模型**，2026 年 3 月发布。官方报告它：

* 复杂 Layout
* 数学
* 表格
* 多语言
* Figure / Diagram
* 结构化输出
* 15+ layout block 类型
* PDF/image → Markdown/HTML/JSON ([GitHub][5])

Block 类型包括：

```text
text
section-header
caption
footnote
table
image
figure
diagram
equation-block
code-block
page-header
page-footer
complex-block
...
```

这显然比：

```text
gemma3:4b
+ 我们自己提示它“请识别教材”
```

更对口。

而且它就是 **4B**，不是 9B/70B。

### 所以我的建议是：

先不要训练。

先拿同一 PDF 做：

```text
Gemma 4B
vs
Chandra OCR 2 4B
vs
MinerU
vs
Marker
```

重点比较：

```text
正文漏字
Figure漏图
Figure编号
表格
公式
阅读顺序
```

如果 Chandra 本地跑得动，它可能很适合作为：

```text
Document Vision Provider
```

而不是普通 Gemma。

不过有一点需要注意：Chandra 的代码是 Apache-2.0，但当前官方 README 明确说**商业 self-hosting 需要另外看许可**，所以如果以后你的软件商业化，要单独核查模型许可。([GitHub][6])

# 5. olmOCR 我不建议现在拿来当默认模型，但非常值得“抄作业”

olmOCR 现在是 7B 文档 VLM，支持：

* PDF / PNG / JPEG → Markdown
* equations
* tables
* handwriting
* complex formatting
* natural reading order
* figures / multi-column / insets ([GitHub][7])

它还有一个特别值得你的东西：

## `olmOCR-bench`

它的测试项目不是简单算 OCR 字符准确率，而分别测：

```text
Text Presence
Reading Order
Tables
Math
Headers/Footers
Multicolumn
Old scans
```

而且它特别强调一个事实：

> 数学公式错一个 x/y 可能只算一个字符差异，但语义上是严重错误。

所以它的数学测试会真正检查公式关系，而不是简单 edit distance。([GitHub][8])

### 这个非常值得借给你的 Validator。

以后我们自己的质量评分不要只是：

```text
coverage = 98%
```

而应该：

```text
Text Coverage       99%
Reading Order       PASS
Numerics            PASS
Equations            PASS
Tables               PASS
Figures              5/5
Styles               96%
```

**第一，不训练。**

先 A/B 测：

```text

```

同一张 8 页 PDF。

**第二，不让这些项目直接取代你的软件。**

你的 PyQt、SQLite、缓存、Review、FigureGroup、Final/Export 都已经做得很好。

只让它们成为：

```text
Document Parser Providers
```

**第三，下一阶段暂时不要叫 Phase 10，也先别继续改 Prompt。**

建议：

# Phase 9.5.2 — Open-source Document Engine Benchmark & Fusion

只做：

```text
同一个PDF
↓
四个解析器
↓
输出统一DocumentPageEvidence
↓
逐页比较
↓
决定谁进入正式Pipeline
```

验收表应该直接长这样：

| Page |        Engine | Missing Text | Figure Recall | Figure ID | Table | Formula | Reading Order | Time |
| ---- | ------------: | -----------: | ------------: | --------: | ----: | ------: | ------------: | ---: |
| 4    | Current Gemma |            … |             … |         … |     … |       … |             … |    … |
| 4    |        MinerU |            … |             … |         … |     … |       … |             … |    … |
| 4    |        Marker |            … |             … |         … |     … |       … |             … |    … |
| 4    |       Docling |            … |             … |         … |     … |       … |             … |    … |

然后我们再决定最终是：

```text
PyMuPDF + MinerU
```

还是：

```text
PyMuPDF + Marker + Chandra
```

或者：

```text
Docling作为DOM + Chandra作为疑难块VLM
```

我目前最看好的组合其实是：

> **PyMuPDF 原生真值 + MinerU/Docling 做布局骨架 + Chandra 做疑难视觉块 + DeepSeek API 做文本结构裁决。**

这比“纯 OCR + DeepSeek”强得多，也比“整页 Gemma → Markdown”更符合现有成熟开源项目的发展方向。MinerU 本身已经把图片/图注、公式、表格、阅读顺序和 OCR 条件启用做成了完整文档解析系统；Docling则把这些结果统一为一个可序列化文档模型；Marker则证明了“只在必要时调用 OCR/VLM”的混合策略是可行的。([GitHub][2])

另外提醒一个工程问题：**不要直接复制这些仓库的代码进项目而不检查许可证。** Docling 是 MIT；olmOCR 是 Apache 2.0；Marker 代码本身是 Apache 2.0，但它的模型权重另有使用限制；MinerU 目前是 Apache 2.0 加附加商业/在线服务条款。([GitHub][4])
